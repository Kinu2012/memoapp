# memoapp

ブラウザ上で動作するシンプルなメモアプリです。

初期版では **SQL.js を利用してSQLiteをブラウザ上で動かし、SQLiteデータベースをlocalStorageへ保存する構成**を採用しています。

その後、「この規模のメモアプリにSQLiteは本当に必要なのか」という疑問から、SQLiteを使用せず **JSON + localStorageのみで動作する比較版**を作成し、構成や実装方法の違いを検証しました。

---

## 主な機能

* メモの新規作成、編集、削除
* 入力内容の保存
* 保存状態の表示

  * 変更あり
  * 保存中
  * 保存しました
* タイトルをクリックするとメモ詳細を表示
* ページ再読み込み後も保存データを保持

## SQLite版の構成

SQLite版では、SQL.jsを利用してブラウザ内でSQLiteを動作させています。

メモの追加・編集・削除はSQLで行い、SQLiteデータベースをバイナリとして出力した後、Base64文字列へ変換してlocalStorageへ保存しています。

処理の流れは以下の通りです。

`画面 → JavaScript → SQL.js / SQLite → Base64変換 → localStorage`

SQLite自体をPCへインストールする必要はありません。

また、SQLiteはブラウザ内で動作しているため、ブラウザを閉じた後もデータを保持するためにはlocalStorageへの保存が必要です。

---

## JSON版の構成

比較検証のため、SQLiteおよびSQL.jsを使用しないバージョンも作成しました。

JSON版では、メモをJavaScriptの配列・オブジェクトとして管理し、`JSON.stringify()`でJSON文字列へ変換してlocalStorageへ保存します。

処理の流れは以下の通りです。

`画面 → JavaScriptの配列 → JSON変換 → localStorage`

外部ライブラリは使用していません。

---

## SQLite版とJSON版の比較

| 項目       | SQLite版                   | JSON版                            |
| -------- | ------------------------- | -------------------------------- |
| 画面       | HTML + CSS                | ほぼ同じ                             |
| 操作処理     | JavaScript                | JavaScript                       |
| データ管理    | SQL.jsでSQLiteを動作          | JavaScriptの配列・オブジェクト             |
| 追加・編集・削除 | SQL文                      | 配列の追加・置換・絞り込み                    |
| 保存形式     | SQLiteバイナリをBase64文字列へ変換   | JSON文字列                          |
| 保存場所     | `localStorage` の `memoDB` | `localStorage` の `memoAppJsonV1` |
| 外部ライブラリ  | SQL.js / WASM             | なし                               |
| 既存データ    | SQLite版のメモ                | 別管理・自動移行なし                       |

## 比較検証

今回のメモアプリでは、

* メモの追加
* 編集
* 削除
* 一覧表示
* データ保存

という比較的シンプルなCRUD処理が中心です。

この範囲であれば、SQLiteを使用しなくてもJSON + localStorageだけで同じ機能を実現できました。

JSON版ではSQL.jsやSQLiteを扱う処理が不要になり、データ保存までの構成も単純になりました。

そのため、現在の機能規模に限れば、JSON版の方がシンプルな構成だと考えています。

一方でSQLiteには、SQLを利用してデータを構造的に操作できる利点があります。

例えば、

* 複数条件を組み合わせた検索
* 並び替え
* 集計
* タグやカテゴリなど複数データの関連付け
* 複数テーブルを利用したデータ管理

といった機能が増える場合は、SQLiteを利用するメリットが大きくなると考えられます。

---

## SQLiteが担っている役割

本アプリでは、SQLiteはデータを永続保存する場所そのものではありません。

SQLiteは主に、

* メモをデータベースとして構造化して管理する
* `SELECT`
* `INSERT`
* `UPDATE`
* `DELETE`

などのSQLによってデータを操作する役割を担っています。

ブラウザを閉じた後もデータを残す役割はlocalStorageが担当しています。

つまり、

* **SQLite：データ管理**
* **localStorage：永続化**

という役割分担になっています。

---

## データベース復元失敗時の処理

SQLite版では、localStorageに保存されたSQLiteデータベースの復元に失敗した場合、新しいデータベースを生成するようにしています。

これは破損したデータを復旧する処理ではなく、**データベースの読み込み失敗によってアプリ全体が起動できなくなることを防ぐための処理**です。

---

## 検証から得られたこと

今回の比較から、SQLiteの必要性は単純なメモ件数だけでは判断できないと考えました。

重要なのは、

* データ構造
* 検索条件の複雑さ
* データ同士の関連性
* 今後追加する機能

です。

現在のようなシンプルなメモアプリであれば、JSON + localStorageでも十分実装できます。

一方で、タグ管理や複雑な検索、複数テーブルを利用する機能へ拡張する場合はSQLiteの利点が大きくなります。

また、複数端末や複数ブラウザから同じメモへアクセスする本格的なアプリに発展させる場合は、localStorageやブラウザ内SQLiteではなく、

`フロントエンド → API / バックエンド → サーバー側データベース`

のような構成へ変更する方が適切だと考えています。

## 工夫した点

### 保存処理の安定性

保存処理には `try/catch` を使用し、保存処理でエラーが発生してもアプリ全体が停止しないようにしています。

### 保存状態の表示

「変更あり」「保存中」「保存しました」などの状態を表示し、編集内容が保存されたか分かりやすくしました。

### 選択中メモの表示

現在編集中のメモが分かるよう、リスト上でハイライト表示しています。

### SQLite構成の再検証

初期実装をそのまま正解とせず、SQLiteを使用しないバージョンを実際に作成して比較しました。

その結果、現在の規模ではSQLiteが必須ではないことと、SQLiteが有効になる条件について整理することができました。

## 使い方

このアプリはブラウザのみで動作します。

1. `index.html` をブラウザで開きます
2. メモを作成・編集します
3. データは同じブラウザのlocalStorageへ保存されます

インストールやビルド作業は不要です。

※ 保存データはブラウザごとに管理されるため、他の端末や別ブラウザからはアクセスできません。
